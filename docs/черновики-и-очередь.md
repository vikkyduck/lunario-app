# Черновики и очередь отправки

По внешнему разбору безопасности от 16.09.2026. Здесь — что уже сделано, как это устроено и что осталось
подключить, когда закончится перестройка фронтенда.

## Что было не так

Три свойства, которых у приложения не было, и каждое проверено на настоящем коде:

1. **Запись жила только в поле ввода.** Перезагрузка страницы — и несохранённого текста нет.
2. **Повтор создавал дубль.** Ответ потерялся, человек нажал «Сохранить» ещё раз — в дневнике две одинаковые записи.
3. **Отказ посередине входа оставлял ни с чем.** Код гасился одним запросом, почта привязывалась другим:
   сбой между ними — и код уже нельзя использовать, а вход не состоялся.

Плюс: `merged: true` означало лишь, что устройство переключилось на другой аккаунт, — записи, сделанные до
входа, оставались у брошенного гостя и пропадали из виду. И `clean(b.code, 6)` обрезал код, поэтому «1234567»
подходил вместо «123456».

## Что сделано на сервере

| Файл | Что делает |
|---|---|
| `backend/sync.mjs` | `transaction()` (запрещает `async` внутри — база синхронна), `AppError`, `publicError()` — перевод ошибок SQLite в честный ответ, `saveJournalOperation()` — запись и квитанция одной транзакцией |
| `backend/transfer.mjs` | подписанное приглашение перенести записи гостя и сам перенос одной транзакцией по реестру личных данных |
| `backend/identity.mjs` | `verifyLogin()` — проверка кода, привязка аккаунта, новая сессия и погашение кода **одной транзакцией**; ровно шесть цифр; повреждённая cookie не роняет запрос |
| `backend/schema.mjs` | миграция 13 — таблица `sync_receipts` |
| `backend/server.mjs` | `GET /api/auth/session`, `POST /api/sync/journal`, `POST /api/account/transfer`, `PRAGMA busy_timeout` |

Два правила, которые легко нарушить при правках:

* **Кука ставится только после `COMMIT`.** Иначе при откате у человека останется кука несуществующей сессии.
* **Счётчик неверных попыток фиксируется даже при отказе.** Поэтому `verifyLogin` при неверном коде не бросает
  исключение (оно откатило бы счётчик), а возвращает решение, и транзакция закрывается штатно.

`POST /api/journal` остался прежним: старый клиент и старая оболочка продолжают работать.

## Что сделано на клиенте

`site/sync.js` — самостоятельный модуль, к приложению **пока не подключён**: `site/app.js` сейчас переписывается,
и трогать его нельзя. Модуль делает ровно то, чего не хватало:

* текст ложится в хранилище браузера **до** отправки, и «сохранено на устройстве» говорится только после
  подтверждения браузером (`complete` у транзакции), а не когда мы попросили;
* у операции есть имя, и при повторах оно не меняется — поэтому сервер узнаёт повтор и не пишет второй раз;
* перед каждой отправкой модуль спрашивает `/auth/session`: человек мог выйти и войти другим, чужой черновик
  отправлять нельзя;
* ответ проверяется по квитанции: `200` с HTML (страница-заглушка Wi-Fi, старая оболочка) — это ошибка, а не успех;
* повторы — пять попыток с растущей задержкой и разбросом, `Retry-After` учитывается, счётчик переживает перезагрузку.

### Про шифрование — честно

Записи в хранилище зашифрованы ключом AES-GCM, созданным этим браузером и помеченным **неизвлекаемым**:
его байтов в JavaScript не существует. Это защищает от случайного чтения файлов профиля.

Это **не** защищает от кода, уже выполняющегося на странице приложения, и от того, кто сидит за разблокированным
устройством. Настоящий сейф требует пароля от человека — а значит, отдельного разговора о том, что делать,
если пароль забыт. Для черновиков, живущих до первой удачной отправки, такой размен разумен; для долгого
хранения — нет, и это надо решать отдельно.

## Как подключить (одна строка)

Когда перестройка фронтенда закончится, в `site/index.html` добавить рядом с остальными скриптами:

```html
<script src="/app/sync.js?v=46"></script>
```

и добавить `'/app/sync.js?v=' + V` в `SHELL` внутри `site/sw.js`, а `sync\.js` — в регулярку `index.html`
в `tools/bump-version.mjs`.

Дальше в `site/app.js`, там где сейчас запись уходит на сервер напрямую:

```js
// было
const r = await api('/journal', { method: 'POST', body: JSON.stringify({ text, kind }) });

// стало: сначала на устройство, потом на сервер — и повтор не задвоит
LUN_SYNC.onNotice(toast);                       // один раз при старте
const op = await LUN_SYNC.saveJournal(text, S.user.id, kind);
if (op && op.state === 'synced') { /* запись в аккаунте, можно очищать поле */ }
else { /* текст сохранён на устройстве; поле НЕ очищаем */ }
```

И при старте приложения — `LUN_SYNC.resume(S.user.id)`, чтобы разобрать то, что осталось с прошлого раза.

**Поле очищается только когда `state === 'synced'`.** Это и есть всё правило: не обещать того, чего не сделали.

## Что осталось за рамками

Сделан один сценарий — запись дневника. Настроение, желания, привычки, фото и правки подключать **по одному**:
у каждого свои правила конфликтов, и менять адрес в готовом вызове недостаточно. Порядок и разбор случаев —
в исходном документе разбора (разделы 5 и 9).
